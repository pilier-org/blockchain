## 0. Ориентация для исполнителя

**Что за проект.** Pilier — одиночная (solo) блокчейн-сеть на Polkadot SDK / FRAME, язык Rust,
модель Proof-of-Authority (фиксированный набор валидаторов, а не открытый стейкинг). Рабочая
директория репозитория блокчейна — корень этого дерева (там `Cargo.toml` воркспейса, папки `node/`,
`runtime/`, `pallets/`). Бинарь называется `pilier-node`. Все палеты берутся из git-ветки
`stable2512` polkadot-sdk (декабрьский стабильный релиз 2025).

**Что требуется сделать (одним предложением).** Сейчас набор авторитетов зашит в генезис и
неизменяем; нужно ввести палету `pallet-session` (сменяемые сессионные ключи, питает Aura и
GRANDPA), совет `pallet-collective` (голосование действующих валидаторов) и небольшую свою палету
набора валидаторов, чтобы валидаторов можно было **добавлять и удалять голосованием** совета (а также
корневым ключом Sudo как аварийным рычагом), и пересоздать генезис со всей этой машинерией и с
раскладкой казны, приведённой к публичной токеномике `pilier.dev`.

**Что сюда сознательно не входит (решено 2026-07-19).** Перенастройку комиссии — деление 95 % автору
блока / 5 % в Civic Treasury вместо нынешнего сжигания — из этого плана вынесли. Это изменение
*конфигурации рантайма*, а не генезиса, ему не нужна пересборка цепочки, и его правильнее сделать
отдельным бесфорковым апгрейдом уже после того, как здесь доказана сама обновляемость (см. «НЕ-область»
и Фазу 6). Поэтому блок комиссии в этом плане не трогаем: комиссия по-прежнему сжигается.

**Золотое правило: компилятор — твой проверяющий.** Точные списки ассоциированных типов у палет
FRAME эволюционируют между версиями. Не полагайся слепо на скелеты кода ниже — они верны по смыслу,
но конкретный набор `type X = ...` подтверждай сборкой. После каждой правки конфигурации запускай
`cargo build --release`; компилятор явно назовёт недостающие или лишние ассоциированные типы
(«missing associated type `Foo`»). Каждый такой пункт разрешай, читая исходник соответствующей
палеты (пути и ссылки — в разделе «Источники»). Это надёжнее любого переписанного руками кода.

**Как запустить проверочную ноду.** Релизная сборка обязательна (debug-сборка ноды крайне
медленная): `cargo build --release`, бинарь — `./target/release/pilier-node`. Одноузловая dev-цепочка:
`./target/release/pilier-node --dev`; сброс её состояния: `./target/release/pilier-node purge-chain
--dev -y`. Логи подробнее: `RUST_LOG=info ./target/release/pilier-node --dev`.

**Где взять точные исходники палет.** Они подтягиваются в
`~/.cargo/git/checkouts/polkadot-sdk-*/<rev>/substrate/frame/<pallet>/src/lib.rs` при первой сборке.
До сборки читай их на GitHub — ссылки в разделе «Источники».

## 1. Инварианты (соблюдать во всех фазах)

- **Индексы палет только добавляются, существующие не перенумеровываются.** Сейчас заняты 0–6:
  System(0), Timestamp(1), Aura(2), Grandpa(3), Balances(4), TransactionPayment(5), Sudo(6) — см.
  `runtime/src/lib.rs`, блок `#[frame_support::runtime] mod runtime`. Новые палеты получают индексы
  **ValidatorSet(7), Session(8), Collective(9)**. **Порядок критичен:** `ValidatorSet` обязан иметь
  индекс МЕНЬШЕ, чем `Session`, потому что genesis-сборка идёт по возрастанию индексов, а
  `pallet-session` на генезисе читает набор у `ValidatorSet` — если бы `Session` собирался раньше,
  он получил бы пустой набор и узел упал бы с паникой `genesis authorities is non-empty`. Подробно —
  `ai/decisions/genesis-build-order.md` (найдено при живой проверке Фазы 3, 2026-07-19; исходно было
  ошибочно Session(7)/ValidatorSet(9)).

- **Стоимость транзакции не меняется — и блок комиссии не трогаем вовсе.** Не изменяй в
  `runtime/src/configs/mod.rs` структуру `WeightToFee` и её `WeightToFeePolynomial`, `parameter_types!`
  с `TransactionByteFee = 10 * MICRO_UNIT` и `FeeMultiplier = Multiplier::one()`, и весь `impl
  pallet_transaction_payment::Config for Runtime` — **включая** поле `OnChargeTransaction =
  FungibleAdapter<Balances, ()>` (это `()` означает «комиссия сжигается»; менять её на распределение —
  отдельная будущая работа, см. «НЕ-область»). Не трогай и константы `UNIT`/`MILLI_UNIT`/`MICRO_UNIT`/
  `EXISTENTIAL_DEPOSIT` в `runtime/src/lib.rs`. В Фазе 5 явно сверишь диффом, что весь этот блок не
  изменился.

- **Свежий генезис — без миграций хранилища.** Цепочка пересоздаётся, поэтому вся новая машинерия
  засевается в генезисе; `type Migrations = ();` в `runtime/src/lib.rs` оставь пустым, кода миграции
  не пиши.

- **Никаких изменений на боевых серверах.** Всё проверяется локально (`--dev` и локальная цепочка).
  Выкатка на живой тестнет — отдельная операционная работа (План 2), не входит сюда.

- **Форматирование и линт.** По завершении каждой фазы: `cargo fmt --all` и `cargo clippy
  --workspace`. Тулчейн закреплён в `env-setup/rust-toolchain.toml`.

- **Свежий под-агент на каждую фазу.** Требование `CLAUDE.md`: один build-агент не переиспользуется
  между фазами (переиспользование молча переводит его на модель сессии). У каждой фазы ниже указан
  свой исполнитель; между фазами всегда спавнится новый агент.

## 2. Архитектура (решено — реализовать как есть, не переизобретать)

Композиция из трёх новых палет плюс уже имеющиеся Aura, GRANDPA, Sudo, Balances, TransactionPayment:

- **`pallet-session` (индекс 8)** — хранит сессионные ключи каждого валидатора и на границах сессий
  передаёт актуальный набор авторитетов в Aura и GRANDPA. Кто именно валидаторы — спрашивает у
  `SessionManager` (это наша палета набора). Когда менять сессию — решает `ShouldEndSession =
  PeriodicSessions` (периодически).

- **`pallet-collective` (индекс 9)** — «совет валидаторов»: тело для голосования. Его члены — это
  суверенные аккаунты действующих валидаторов. Мотиви на приём/исключение валидатора, набрав порог
  голосов (75 %, см. ниже), исполняет вызов нашей палеты набора.

- **Своя палета `pallet-validator-set` (индекс 7)** — хранит список валидаторов; реализует
  `pallet_session::SessionManager` (отдаёт этот список session); открывает вызовы
  `add_validator`/`remove_validator` под origin «порог голосов совета ИЛИ root (Sudo)»; при изменении
  списка синхронизирует членов совета (через хук смены членства). Засевается в генезисе тремя
  текущими валидаторами.

**Поток данных при приёме нового валидатора.** Совет голосует за мотиви «добавить валидатора X» →
по достижении порога исполняется `ValidatorSet::add_validator(X)` → список набора обновляется, члены
совета синхронизируются → на ближайшей границе сессии `pallet-session` берёт новый список у
`SessionManager` и обновляет авторитетов Aura и GRANDPA → узел X начинает производить и финализировать
блоки (при условии, что X заранее выставил свои сессионные ключи вызовом `session.set_keys`).

**Два вида ключей (важно понимать при засеве генезиса).** У валидатора есть суверенный аккаунт
(`AccountId`, он же голос в совете и владелец записи в наборе) и сессионные ключи `SessionKeys { aura,
grandpa }` (лежат на узле, сменяемы). Для трёх текущих валидаторов суверенный аккаунт — это аккаунт,
производный от их **aura**-ключа (так уже устроен текущий генезис: aura-публичный ключ используется и
как `AccountId`). Новые ключи для существующих трёх заводить не нужно.

**Почему такая композиция, с ценой альтернатив.** Своя палета `pallet-validator-set` — это примерно
150 строк кода один раз, без внешней зависимости. Альтернатива — внешняя палета
`substrate-validator-set`: экономит эти ~150 строк, но добавляет постоянную зависимость, которую
придётся вручную держать в синхроне с веткой `stable2512` при каждом апгрейде polkadot-sdk (риск
рассинхрона версий и заклиненного апгрейда). При приоритете «поддерживаемость» разовые 150 строк
дешевле бессрочного риска рассинхрона. Ещё альтернатива — привязать набор к `pallet-membership`: та же
логика, но связка «членство → session» более косвенная и всё равно требует своего адаптера
`SessionManager`, то есть не экономит почти ничего и добавляет лишний слой. Выбор: своя палета; её
логику сверять по `substrate-validator-set` как по образцу, но код держать свой в воркспейсе.

Отклонённые для этого плана как преждевременные (см. «НЕ-область»): **деление комиссии 95/5**
(вынесено в отдельный бесфорковый апгрейд после Фазы 6 — комиссия пока сжигается); **белый список
переводов** (отложен по решению Алекса — на тестнете не требуется); **инфляционная субсидия**
(отменена — валидаторы кормятся из фиксированного Bootstrap Pool, эмиссия остаётся фиксированной);
**вестинг команды** (отдельная палета, когда появится команда); **tPIL** (управляющий орган — совет).

## Фаза 1 — Своя палета `pallet-validator-set` (изолированно)

**Исполнитель:** Sonnet, свежий спавн.

**Артефакт:** новый член воркспейса `pallets/validator-set`, который компилируется и проходит свои
модульные тесты.

**Образец для копирования.** Возьми структуру и boilerplate из существующей `pallets/template`
(это скелет в том же репозитории, не подключённый к рантайму, специально как пример) — `Cargo.toml`,
`src/lib.rs`, `src/mock.rs`, `src/tests.rs`. Логику управления набором и реализацию `SessionManager`
сверяй с внешней палетой `substrate-validator-set` (ссылка в «Источниках») как с образцом, но код
пиши свой.

**Что должна содержать палета:**
- Хранилище `Validators: StorageValue<_, Vec<T::AccountId>, ValueQuery>` — текущий набор.
- Конфигурация `Config`: `type RuntimeEvent`; `type AddRemoveOrigin: EnsureOrigin<Self::RuntimeOrigin>`
  (origin, которому позволено менять набор — в рантайме подставим «совет ИЛИ root»); `type
  MembershipChanged: ChangeMembers<Self::AccountId>` (куда сообщать о смене состава — в рантайме
  подставим совет, чтобы члены совета = набор); `type MinValidators: Get<u32>` (нижняя граница,
  чтобы нельзя было опустить набор ниже, например, 1, — защита от сноса сети). `WeightInfo` можно
  начать с `()`.
- Вызовы `add_validator(origin, who: T::AccountId)` и `remove_validator(origin, who: T::AccountId)`,
  оба через `T::AddRemoveOrigin::ensure_origin(origin)?`. `add` добавляет, если ещё нет; `remove`
  удаляет, если есть и если после удаления останется не меньше `MinValidators`; оба обновляют
  `Validators`, шлют событие и вызывают `T::MembershipChanged::change_members_sorted(...)`.
- Генезис `GenesisConfig { initial_validators: Vec<T::AccountId> }`, заполняющий `Validators`.
- Реализация `impl<T: Config> pallet_session::SessionManager<T::AccountId> for Pallet<T>`:
  `new_session(_) -> Some(Validators::get())`, `start_session(_) {}`, `end_session(_) {}`. Именно эта
  реализация связывает набор с session.

**Критерии приёмки:** `cargo build -p pallet-validator-set` проходит; `cargo test -p

## Фаза 2 — Зависимости и конфигурация session + нашей палеты в рантайме

`pallet-session` и `pallet-collective` (git polkadot-sdk, branch `stable2512`, `default-features =
false`) — тем же паттерном, что уже стоят `pallet-aura`, `pallet-grandpa` и т.д. В `runtime/Cargo.toml`
добавь `pallet-session.workspace = true`, `pallet-collective.workspace = true`,
`pallet-validator-set = { path = "../pallets/validator-set", default-features = false }`, и внеси их в
списки features `std`, `runtime-benchmarks`, `try-runtime` по образцу соседних палет. (`pallet-collective`
объявляется здесь, а подключается в Фазе 4 — так зависимости не трогаются повторно.)

**Конфигурация.** В `runtime/src/lib.rs` добавь `ValidatorSet` (индекс 7) и `Session` (индекс 8) в
`#[frame_support::runtime] mod runtime`. В `runtime/src/configs/mod.rs` добавь `impl
pallet_session::Config for Runtime` и `impl pallet_validator_set::Config for Runtime`. Скелет session
(сверить точный набор типов с исходником — золотое правило):
```rust
parameter_types! {
    pub const Period: BlockNumber = 100; // ~10 минут при 6 с/блок, удобно для тестнета
    pub const Offset: BlockNumber = 0;
}
pub struct ValidatorIdOf; // Convert<AccountId, Option<AccountId>> — тождество
impl sp_runtime::traits::Convert<AccountId, Option<AccountId>> for ValidatorIdOf {
    fn convert(a: AccountId) -> Option<AccountId> { Some(a) }
}
impl pallet_session::Config for Runtime {
    type RuntimeEvent = RuntimeEvent;
    type ValidatorId = AccountId;
    type ValidatorIdOf = ValidatorIdOf;
    type ShouldEndSession = pallet_session::PeriodicSessions<Period, Offset>;
    type NextSessionRotation = pallet_session::PeriodicSessions<Period, Offset>;
    type SessionManager = ValidatorSet;      // наша палета из Фазы 1
    type SessionHandler = <SessionKeys as sp_runtime::traits::OpaqueKeys>::KeyTypeIdProviders;
    type Keys = SessionKeys;                 // уже объявлены в lib.rs
    type WeightInfo = ();
    // Точный полный список типов подтверди сборкой и исходником session/src/lib.rs.
}
impl pallet_validator_set::Config for Runtime {
    type RuntimeEvent = RuntimeEvent;
    type AddRemoveOrigin = frame_system::EnsureRoot<AccountId>; // на Фазе 4 заменим на «совет ИЛИ root»
    type MembershipChanged = ();  // на Фазе 4 заменим на совет
    type MinValidators = ConstU32<1>;
    type WeightInfo = ();
}
```
Замечание: у GRANDPA в `configs/mod.rs` подними `MaxSetIdSessionEntries` с 0 до ненулевого
(например `ConstU64<168>`), раз теперь есть смена сессий. `MembershipChanged = ()` допустимо, если
тип принимает `()`; иначе подставь заглушку-`ChangeMembers`, реализующую пустые методы.

**Выбор `Period = 100` (альтернатива с ценой).** 100 блоков ≈ 10 минут — компромисс: короче (например
10 блоков ≈ 1 минута) удобнее для быстрой демонстрации смены набора, но чаще гоняет ротацию сессии и
засоряет логи; длиннее (например 600 ≈ 1 час) ближе к боевому, но демонстрация приёма валидатора ждёт
дольше. Цена изменения нулевая — одна константа; 100 выбрано как удобное для тестнета значение.

**Критерии приёмки:** `cargo build --release` проходит; `cargo test --workspace` проходит.
